Deployment & CloudHub

CloudHub 2.0 Architecture

6 min read Lesson 3 of 11 in Deployment & CloudHub

CloudHub 2.0 rebuilds the same basic promise as CloudHub 1.0 — fully managed deployment with no infrastructure to maintain — on a fundamentally different foundation: containers orchestrated by Kubernetes instead of dedicated virtual machines.

Replicas Instead of Workers

Where CloudHub 1.0 provisions dedicated VM-based workers, CloudHub 2.0 deploys applications as containerized replicas running as pods on a shared, MuleSoft-managed Kubernetes cluster. Each replica still runs one Mule application, preserving the same application-level isolation model conceptually, but the underlying compute is a container rather than a full VM — which is what unlocks faster startup and more efficient resource use, since containers start in seconds rather than the minutes a fresh VM boot requires.

What Changed, Side by Side

AspectCloudHub 1.0CloudHub 2.0
Compute unitDedicated worker VM (AWS EC2)Containerized replica (Kubernetes pod)
Deployment speedSeveral minutes (full VM boot)Seconds to low minutes (container start)
Sizing granularityFixed vCore tiers (0.1, 0.2, 1, 2, 4, 8...)More granular vCPU/memory combinations
Isolation modelOne application per VM, strong hardware-level isolationOne application per replica, container-level isolation
NetworkingShared or dedicated load balancer add-onPrivate Spaces with built-in VPC-style network isolation
Underlying infrastructureAWS EC2 instances managed by MuleSoftKubernetes-based platform managed by MuleSoft
ScalingManual addition of workersReplica count adjustable with finer increments, supports more dynamic scaling

Faster, More Granular Deployments

Because replicas are containers rather than full VMs, redeploying a new application version is noticeably faster — the platform can start new replica containers, confirm they're healthy, and shift traffic over in a fraction of the time a new worker VM would take to boot. This shortens the feedback loop for teams deploying frequently, and it also makes it more practical to right-size applications, since vCPU and memory can be allocated more granularly than CloudHub 1.0's fixed vCore tiers allowed.

Improved Isolation with Private Spaces

CloudHub 2.0 introduces Private Spaces, a network isolation boundary conceptually similar to a VPC, within which an organization's applications run isolated from other customers' workloads at the network layer, not just the application layer. This makes it straightforward to set up private connectivity to on-premises systems or other cloud VPCs (via VPN or peering) without the address space and routing constraints that existed in CloudHub 1.0's shared network model.

Deployment Example

anypoint-cli-v4 runtime-mgr:application:deploy orders-api \
  target/orders-api-1.0.0-mule-application.jar \
  --target cloudhub2-space-us-east-1 \
  --runtime 4.6.0 \
  --replicas 2 \
  --vCores 0.2 \
  --environment Production

Migration Considerations

CloudHub 2.0 is not simply a drop-in replacement for CloudHub 1.0 applications; migrating typically requires reviewing static IP dependencies (since IP allocation works differently under Private Spaces), re-provisioning environment configuration under the new target, and validating that any CloudHub 1.0-specific features an application relies on have an equivalent in CloudHub 2.0. Most organizations run a migration project rather than a simple redeploy-and-switch.

  • CloudHub 2.0 replaces dedicated VM workers with containerized replicas running on a Kubernetes-based platform.
  • Container-based replicas start dramatically faster than CloudHub 1.0 worker VMs, shortening deployment time.
  • Sizing is more granular, allowing finer vCPU/memory allocation than CloudHub 1.0's fixed vCore tiers.
  • Private Spaces add network-layer isolation and simplify private connectivity to on-prem or other cloud networks.
  • Moving an application from CloudHub 1.0 to 2.0 is a migration project, not an automatic drop-in switch.
